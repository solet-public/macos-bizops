1. **The fleet does not work end-to-end** on a seed-born deployment (Issue 1 —

one-off agent mistakes — fixing the agent's prompt-of-the-moment does not fix
the next birth. The seed should drive the agent to run a setup **wizard to
completion**, not host an offer desk.

## Issue 1 — BLOCKING: fleet coordination does not work end-to-end

**Severity:** Blocking (the operator cannot run the multi-role fleet the docs
advertise).

**What happened:** The fleet launchers exist and a labeled session does start
(this feedback was written from a `HOMUNCULUS_AGENT_SESSION_LABEL=Git-Controller`
session), but coordination between sessions does not function. The rendered
`client/dax-fleet.zsh` currently carries an active, unresolved diagnostic:

```
# DIAGNOSTIC 2026-07-23: --remote-control "$role" temporarily removed to
# test whether child/remote sessions suppress hook execution.
```

`--remote-control` is the mechanism the runbook (line 281) and the shipped
`fleet_functions.zsh.template` (lines 20–24) name as "what lets a coordinator
session drive/monitor worker sessions." With it removed there is no
coordinator-drives-peer path — and it was removed precisely to chase a deeper
suspicion: that **child/remote Claude Code sessions suppress hook execution.**
That matters because the entire no-MCP coordination stack is hook-borne:

- peer messaging + role binding come from each session's `SessionStart` hook →
  `rename` skill → `dax watch` registered-presence watcher, and
- idle wake comes from the user-scope `Stop` hook running `dax wake`.

If hooks don't fire in labeled child/remote sessions, none of that works. The
runbook already records this exact fragility as a field observation (lines
131–134: "a fleet session in another repo got no [hook]"), and the user-scope
hook install (Step 2 ruling, 2026-07-22) was the mitigation — yet the current
diagnostic indicates the child/remote-session case is still not reliable.

**Compounding gap — the git-controller gate is not shipped.** The runbook's own
Step 4a (line 285) states the seed does NOT ship the gate hooks
(`git_controller_gate.py`, `_git_controller_lex.py`, `_git_controller_walker.py`),
yet a real fleet sharing one clone needs them (or an equivalent) to be safe, and
the operator's environment references them as globally wired. So "the fleet is a
supported pattern" is only true if the operator re-authors load-bearing pieces
the seed doesn't include — which the runbook mentions in passing rather than as
a required fleet-setup workstream.

**Recommended fix:**
1. **Ship a fleet smoke test as part of Step 4a**, run BEFORE the operator
   builds N role functions: launch one extra labeled session and prove it
   (a) registers presence, (b) receives a peer message, (c) wakes from idle.
   The operator should learn at setup time whether the fleet works on their
   Claude Code build/policy — not after wiring 14 roles and discovering silence.
2. **Resolve the child/remote-session hook-suppression question in the seed**
   (or document the supported configuration explicitly, including whether
   `--remote-control` is compatible with hook firing on current Claude Code).
   Leaving a diagnostic `# temporarily removed` comment in the shipped-shape
   launcher is a sign this is unfinished, not configured.
3. **Either ship the git-controller gate or stop presenting the gate as a
   ready feature.** If it stays out of the seed, Step 4a should treat
   "obtain/author the gate hooks" as an explicit, sized fleet-setup step.

## Issue 2 — DEFECT (recurrence): the "offer / ask-first" runbook spine still produces lazy agent deferral

**Severity:** High (this is the operator's primary experience complaint, and it
is a recurrence of an already-ruled-on issue).

**What happened:** The operator watched the driving agent skip installation
steps and wait to be asked, and present setup decisions as a menu of questions
instead of investigating and executing.

**Root cause:** `01_hydration_runbook.md` is still pervasively offer-framed —
"probe first, offer, act only under the user's normal tool-approval flow" (line
15); "Step 4a — offer: multi-role fleet coordination (optional)" (line 236);
"Offer this explicitly; do not build it unasked" (line 268); "Ask first, don't
prescribe" (line 270); "Step 5 — optional MCP bridge, ONLY on explicit operator
request" (line 303). Prior feedback `_dax_setup_feedback.md` §3b/§3d plus the
operator ruling of 2026-07-21 ("put the driving agent in the driver's seat")
said to invert exactly this. The seed absorbed the ruling only in spots (line
291 "Do not pitch each plugin as an optional birth-time decision"; line 24 "the
analysis is not optional") while leaving the overall offer-desk spine intact —
so the net felt experience is unchanged.

**Recommended fix:** Rewrite the runbook so its default verb is **investigate →
decide → execute the full setup**, presented to the agent as a wizard it runs to
completion. Reserve operator questions for the genuinely divergent, destructive,
or credential-bearing choices. Add a **hydration completion checklist** the
agent must satisfy (every core feature reached, every consent gate explicitly
raised) so "I offered nothing and stopped early" is a visible failure, not a
silent default.

## Issue 3 — DEFECT: decision points don't state their behavioral impact or why they're even decisions

**Severity:** Medium–High (this is the operator's "confusing terms, no
description of impact" complaint).

**What happened:** Setup decisions were surfaced to the operator in
platform-internal jargon — MCP bridge vs. no-MCP, development channel,
remote-control, shared-vs-separate Postgres, the git gate — without a plain
statement of *how the homunculus's or Claude's observable behavior changes with
each choice*, or why the choice exists at all.

**Root cause:** The "connectivity glossary" (lines 59–79) and the fleet/MCP
decisions are described in terms of the mechanism, not the outcome. The ONE
decision that does this right is the git-gate paragraph (line 285): it states
the tradeoff in observable terms ("enabling the gate BLOCKS the Task tool for
every non-controller session — and that block is the gate's PRIMARY PURPOSE").
Every other decision should read like that one.

**Recommended fix:**
- Give every operator decision a two-line **"If yes, the homunculus/your Claude
  sessions behave like X; if no, like Y"** in observable terms. Use the
  git-gate paragraph as the template.
- **Drop decisions that aren't real choices in the target environment.** MCP is
  policy-blocked in this shop (and unusable on Bedrock), so presenting the MCP
  bridge / development channel as co-equal options is pure confusion here. The
  docs should let a profile/environment declare "MCP unavailable" and then stop
  offering it at all, rather than asking the operator to decline it repeatedly.

## Issue 4 — DEFECT: core functionality ships as an opt-in "pitch" the agent silently skips (session ledger is the canonical case)

**Severity:** Medium–High (the operator's literal "if I hadn't asked about the
ledger, you'd never have mentioned it").

**What happened:** The session ledger — the substrate for this platform's own
"ask the homunculus what happened" recall pattern — was never set up until the
operator explicitly asked whether they could query it.

**Root cause:** `claude_code_filesystem_session_source_plugin/knowledge_base/`
`hydration_guidance.md` frames the ledger as a **"Pitch"** that is **"opt-in
rather than on by default"**, with setup performed only **"On an explicit yes."**
Layer that onto the offer-desk runbook spine (Issue 2) and the predictable
result is: the agent never proactively surfaces it, so a core capability stays
dark. Note the ledger genuinely IS a consent boundary — it reads the operator's
local `~/.claude/` transcript files — so the fix is NOT "auto-enable silently."
The bug is conflating **"consent-gated"** with **"optional/skippable."**

**Recommended fix:** Split the taxonomy the docs use into three buckets and label
every feature as exactly one:
- **Core, no consent needed** → the wizard just does it.
- **Core, consent-gated** → the wizard MUST reach it and MUST explicitly ask
  (with the observable-behavior framing from Issue 3); silently skipping it is a
  defect. The session ledger belongs here.
- **Genuinely optional / environment-dependent** → offer only where relevant
  (e.g. MCP where policy permits).

A hydration completion checklist (Issue 2) that enumerates every consent-gated
core feature is what prevents the silent skip.

## What worked (keep it)

- **The homunculus is healthy and MCP-free operation is solid.** `dax health`
  is green; `dax search` and `dax call` return rich, correct results. For an
  MCP-blocked environment, the no-MCP `dax` command is the right primary
  interface, and it works out of the box.
- **KB search quality is genuinely good.** Process descriptions returned by
  `dax search` are detailed enough to drive `dax call` correctly without
  guessing argument shapes.
- **Per-homunculus DB isolation and provenance/lineage tracking are clean.**
  `PROVENANCE.json`'s lineage chain and the `root_manifest.yaml` contract are
  legible, and the isolation model was praised in prior feedback too.
- **Single-session operation (`claude-dax`) works.** The problems are all in the
  fleet layer and the setup experience, not the base homunculus.
- **The feedback loop itself is functioning — just incompletely.** Two prior
  seed-feedback reports existed, and SOME of their points made it into
  `a01575d31` (install-all-now plugin activation; "analysis is not optional").
  The mechanism works; it just needs to absorb the operator's 2026-07-21 "driver's
  seat" ruling fully, not partially.
